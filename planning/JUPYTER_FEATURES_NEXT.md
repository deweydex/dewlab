# Five Jupyter features worth having in dewmini

A brief for a future session, written to be read cold. Nothing here has been
started; nothing here is committed. It is a proposal with the groundwork
done, not a plan already agreed.

**Origin.** Josh asked, after the workbench work landed (PR #90, merged
2026-08-31): *"Are there any other features in Jupyter notebooks that you
think would be helpful besides widgets?"* This is the considered answer,
written up so it can be acted on in a different session.

**A companion document.** `planning/DATABASE_MODULE_AND_BIGGER_IDEAS.md`
covers the larger and more speculative ground — why the notebook form fails
for databases, what the empty `tutorials/database-methods/` module would
need, and the path from notebook to program. Read that one for scope; this
one for the near-term list.

**Widgets are deliberately out of scope** here. They were deferred by Josh
earlier and remain the one genuine capability gap; they are a separate,
larger piece of work and are not one of the five below.

---

## 0. What you need to know if you are starting cold

**dewmini** is dewlab's browser Python workspace — a small notebook at
`compose/dewmini.html`, driven by `compose/dewmini.js`, styled by
`compose/dewmini-style.css`. It runs real Python via Pyodide in a Web
Worker. It is *not* a tutorial page: tutorials are generated by `build.py`
into `site/tutorials/…` and driven by `assets/tutorial-runtime.js`. The two
share an engine (`assets/pyodide-engine.js`, `assets/pyodide-worker.js`) and
a stylesheet (`assets/tutorial-style.css`), which is why a change to either
engine reaches both surfaces — see `DECISIONS_LOG.md` 7.97.

**Who it is for.** Further-education students on three modules: Maths for
Information Technology (MIT-), Programming and Design Principles (PDP-), and
Computational Methods and Problem Solving (CMPS-). Many are new to
programming. This matters to every judgement below: the question is never
"does Jupyter have it" but "does it help someone who is learning".

**What dewmini already has** — checked against the code, not remembered:

| | Where |
|---|---|
| Python and text cells, one shared namespace | `compose/dewmini.js`, `CELL_TYPES` (~line 40) |
| Notebook tabs | `notebooks[]`, `setCells()`, `showNotebook()` |
| Drag to reorder cells | `compose/dewmini.js` ~2150, section marked "drag reorder" |
| Insert seams between cells | `createInsertDivider()` ~568 |
| Run one cell, Run all, Stop | `executeCell()` ~913, `runAllCells()` ~1072 |
| Restart Python | Settings → `initExecutionSection()` ~2293 |
| Markdown text cells | `renderDocMarkdown()` ~508 |
| `.ipynb` and `.py` import, `.ipynb`/HTML/PDF export | ~1200–1240, ~2006 |
| Autocomplete and hover docs (Jedi) | shared engine |
| Variable inspector | `describe_globals()` in `assets/tutorial_tools.py` |
| Two resizable rails, reference, data catalogue | `DECISIONS_LOG.md` 7.99–7.103 |

**Line numbers will drift.** They are given as a starting point; the
function names are the durable anchor. Grep for those.

**Repo conventions the next session must follow** (they are not optional
here, and a PR ignoring them will read as foreign):

- `CONTRIBUTING.md` sets a standing documentation-and-comments requirement.
- `planning/PEDAGOGICAL_STYLE_GUIDE.md` governs naming and comment style in
  anything a student might read.
- `DECISIONS_LOG.md` gets an entry per decision, numbered in sequence
  (7.104 is the most recent), explaining *why* and what the alternative was.
- `tests/MANUAL_CHECKLIST.md` collects what automation cannot reach.
- e2e tests live in `tests/e2e/`; dewmini's are
  `tests/e2e/test_dewmini_workbench.py` (21 tests). They need
  `python3 dev/fetch_pyodide.py` once, ~32 MB.

## The five, in the order I would do them

Features 1 and 2 are a pair and should ship together — the second is far
less useful without the first. Feature 4 is the largest and the one with
implications beyond dewmini; it has its own section at the end.

---

## 1. Execution counters — the `In [3]` numbers

**What.** A small number beside each Python cell showing *when* it last ran,
counting up across the session: the first cell you run is 1, the next 2, and
so on, regardless of where they sit on the page. A cell that has never run
shows nothing.

**Why this is first.** The single most confusing property of notebooks is
that they run **in the order you press Run, not top to bottom**. A student
whose cell 2 depends on a name defined in cell 5 has a notebook that works
perfectly for them and fails for everyone else — including for themselves
tomorrow, after a reload. Right now nothing on the page says so. dewmini
makes this *more* acute than Jupyter does, not less, because every tab
shares one namespace (`DEWMINI_WORKBENCH.md` §3), so a name can arrive from
a cell that is not even on screen.

This is also the cheapest thing on the list that teaches something real.
Reproducibility is a genuine learning outcome, not a nicety, and this makes
the failure mode visible instead of invisible.

**Extent.** Small. One integer on the cell object, one counter on the
notebook, one badge in the cell header.

- `compose/dewmini.js` ~313, `insertCellAt()`: the cell shape is
  `{ id, type, content, output, error }`. Add `count: null`.
- `executeCell()` ~913: increment a module-level counter and assign.
- `createCellElement()` ~616 builds `.dm-cell-head` (~629) and
  `.dm-cell-actions` (~641). The badge goes in the head.
- `runAllCells()` ~1072 calls `engine.resetPageState()` first, so the
  counter should reset there too — after a Run all, the numbers should read
  1..n top to bottom, which is exactly the point being taught.
- Restart (`initExecutionSection()` ~2293) must clear every count, since
  nothing in the namespace survives.

**Storage.** `saveState()` (~182) writes to `dewmini:notebooks:v1` (key at
~line 21). Adding a field is backward-compatible — `loadSavedState()` (~137)
already tolerates missing fields, and `migrateLegacyCells()` (~123) handles
the pre-tabs shape. **Decision to make and record:** should counts survive a
reload? I would say **no** — the Python session does not survive a reload,
so a count that does would be claiming something false. Clear them on load.

**Jupyter reference.** Jupyter calls this `execution_count`, and it is part
of the nbformat 4 schema. dewmini's `.ipynb` export already writes
`execution_count: null` for every code cell (`compose/dewmini.js` ~1230) —
so this feature has a place to go in the export **already**, and filling it
in makes exported notebooks more faithful. The import side (~2006) currently
ignores the field; it could read it back, though see the storage decision
above for why it probably should not.

**Tests.** Unit tests cannot see this. Add to
`tests/e2e/test_dewmini_workbench.py`: run cell 3 then cell 1, assert the
badges read 2 and 1 respectively — that is the whole feature in one
assertion.

## 2. A stale marker — "this output is older than this code"

**What.** When a cell's code has changed since it last ran, say so: a muted
word or a changed border, cleared the moment it runs again.

**Why.** The natural partner to feature 1, and the other half of "but it
worked". A student edits a cell, does not re-run it, and reads output
belonging to code that no longer exists on the screen in front of them. They
then debug the wrong thing. This is not an exotic case — it is what happens
every time someone fixes a typo and looks up.

**Jupyter does not really do this**, which is worth saying plainly: some
JupyterLab extensions do, the core product does not. So this is not "catch
up with Jupyter", it is "be better than it in a way that matters for
beginners". That makes it a design decision to argue for rather than a box
to tick.

**Extent.** Small, and smaller than it sounds. The mechanism is one more
field: store the cell's content **as it was when it last ran**, and compare.

- Add `ranContent` alongside `count` in the cell shape (~314).
- Set it in `executeCell()` (~913), at the same moment as the count.
- `updateCellChrome()` (~601, just after `createInsertDivider()`) already
  exists precisely to re-style one cell without re-rendering the notebook —
  it currently toggles the error class. This is where the stale class goes.
- The editor already notifies on change (CodeMirror update listener); that
  is the hook for re-running `updateCellChrome()`.

**Watch out for.** Whitespace-only edits will mark a cell stale. That is
arguably correct (the code did change) and arguably noise. I would start
strict — any difference — and only soften it if it annoys in practice.
Record whichever way it goes.

**Tests.** e2e: run a cell, edit one character, assert the marker appears;
re-run, assert it goes.

## 3. Run above / run below

**What.** Two more run commands: everything up to and including this cell,
and this cell and everything after it.

**Why.** With one shared namespace this is the practical repair once
features 1 and 2 have shown the student the problem. Today the options are
one cell or all of them, and "all" throws away a slow computation you did
not need to redo — which is exactly the moment a student stops using the
safe option and starts clicking cells in ad-hoc order again.

"Run below" is also the honest fix after editing a cell midway down: every
cell after it may now be wrong, and nothing else in dewmini says so.

**Extent.** Small-to-medium, and mostly a refactor rather than new logic.
`runAllCells()` (~1072) already does the whole job — the batch loop, the
per-cell try/finally that resets a run button when a run rejects, the
error tally, the status line. It just does it over `cells.filter(python)`.
Generalise it to take a slice.

**One real decision.** `runAllCells()` calls `engine.resetPageState()` first,
so "Run all" always starts from a clean namespace. "Run below" **must not**
do that — the whole point is to keep what the earlier cells defined. "Run
above" arguably should. Get this wrong and the feature silently destroys
work; it is the only part of this item that needs care.

**Where the controls go.** The per-cell action bar (`.dm-cell-actions`,
~641) is the obvious home, but note the toolbar has just been deliberately
thinned (`DECISIONS_LOG.md` 7.102 — the Python and Text buttons were removed
as duplicates of the insert seams). Adding two buttons to every cell cuts
against that. Consider one menu, or keyboard-only, and argue for whichever.

**Jupyter reference.** Jupyter's Run menu has *Run All Above* and *Run All
Below*, and this is one of the more-used menus in the product.

## 4. Maths in text cells

**What.** `$x^2 + 3x$` in a dewmini text cell should render as maths, the
way it already does in a tutorial.

**Why.** Josh teaches Maths for Information Technology. Right now a student
using dewmini to work through a maths problem cannot write the maths — only
the code. For a substantial part of the course, dewmini is currently worse
than paper for expressing what the lesson is actually about.

**This one needs thinking through, and Josh has flagged it as project-wide.**
See §5 below, which is the real content of this item. What follows is the
dewmini-specific mechanics.

**Extent.** Medium — and the trap is that it *looks* small.

The machinery all exists and is already client-side, which is the good news:

- `build.py` `extract_math()` (~482) pulls `$…$` and `$$…$$` out of a
  tutorial's markdown **before** the Markdown converter sees it, using
  `INLINE_MATH_RE` / `DISPLAY_MATH_RE` (~152–153).
- `render_math()` (~565) emits `<span class="dl-math">` holding the escaped
  source TeX — deliberately, so that without JavaScript the reader sees the
  TeX rather than a blank gap.
- `assets/tutorial-runtime.js` `renderMaths()` (~2362) then imports
  `assets/vendor/katex.bundle.js` and calls
  `renderMath(span, span.textContent, isDisplay)` on each span.

So the browser-side renderer is a vendored module with a two-argument-plus-
flag API, ready to call. dewmini can import the same one.

**The part that is not a copy-paste.** `extract_math` exists because
**Markdown mangles TeX**: `$a_i$` comes back with the underscore read as
emphasis, and `$x^2$` can lose its caret. dewmini's text cells go through
`renderDocMarkdown()` (~508), a hand-written client-side renderer — *not*
Python-Markdown. So the extract-then-restore pattern has to be **ported into
JavaScript**, not merely invoked. Calling KaTeX on the output of the existing
renderer will produce wrong maths for exactly the expressions a maths course
uses most. This is the single most likely way to get this feature subtly
wrong.

**The weight.** `assets/vendor/katex.bundle.js` is **266 KB**, plus
`vendor/katex.min.css` at 23 KB, plus `assets/vendor/fonts/` at ~300 KB.
Call it ~590 KB. `DECISIONS_LOG.md` 1.8 established that tutorials fetch it
**lazily**, only when the page's manifest says it has maths, precisely so a
prose-and-code tutorial never pays for it.

dewmini has no manifest and cannot know in advance whether a student will
type maths. The obvious answer is to load KaTeX on first sight of a `$…$` in
a rendered text cell and never again — lazy, same as tutorials, just
triggered by content rather than by a build-time flag.

**The offline bundle is the real decision.** `build.py`
`DEWMINI_ASSET_FILES` (~2977) lists what the downloadable dewmini carries,
and it currently says, in a comment: *"No vendor/katex.min.css (dewmini
renders no maths)"*. That comment becomes false with this feature.
Adding KaTeX and its fonts to the bundle adds ~590 KB to a download whose
stated goal is to be as small as it can be — for a classroom with no
reliable connection, which is the whole reason the bundle exists. That is a
genuine trade, not a formality:

- Include it, and every offline copy grows by ~590 KB whether or not that
  classroom does maths.
- Exclude it, and maths silently fails in exactly the offline setting a
  maths class is most likely to be using.

I would include it and say so in the release notes, but this is Josh's call
and should be recorded as one.

**Also affected.** `buildStandaloneHtml()` (~1308) inlines everything into a
single exported HTML file. If an exported notebook contains maths, that
export needs KaTeX inlined too, or the maths a student wrote will not
survive being sent to someone else — the same class of gap as
`DECISIONS_LOG.md` 7.102's missed boot paths. Check every export path, not
just the one in front of you.

## 5. Maths in markdown, across the whole project

Josh's note, and I think he is right that this is bigger than dewmini.

Right now the project has **one** maths pipeline, and it only serves
generated tutorial pages:

```
tutorials/**/*.md
  → build.py extract_math()      (protect TeX from Markdown)
  → build.py render_math()       (emit <span class="dl-math">TeX</span>)
  → tutorial-runtime renderMaths() (KaTeX, lazily, in the browser)
```

Every *other* place markdown is written or rendered in dewlab is outside it.
Before building anything, someone should enumerate those. From this
session's reading, at least:

- **dewmini text cells** — `renderDocMarkdown()`, client-side. Feature 4.
- **dewmini student notes** — the Workbench rail's Notes section.
- **The authoring editor** (`assets/editor.js`, Milkdown/Crepe) — this one
  already has KaTeX support of its own through Milkdown, so there may now be
  *two* maths renderers in the project with different behaviour. Worth
  checking whether they agree on edge cases.
- **Glossary definitions and examples** (`<slug>.glossary.yaml`) — these
  surface in both the tutorial Reference panel and dewmini's Library rail.
  A maths definition currently cannot contain maths.
- **Practice questions and hints**.
- **The topic map's `plain:` descriptions**
  (`planning/curriculum/topics.yaml`) — plain-English topic explanations for
  a *maths* curriculum, which cannot currently contain a formula.

**The question to settle before writing code** is whether dewlab should have
**one** markdown-with-maths renderer used everywhere, or accept several. One
renderer is the right instinct and the harder job: the build-time path is
Python (`markdown` library) and every other path is JavaScript, so "one
renderer" realistically means *one client-side renderer that the build also
targets*, which is a real refactor of `to_html()` / `place_blocks()`.

**My recommendation:** do **not** fold that refactor into feature 4. Ship
maths in dewmini text cells first, deliberately as a second implementation,
with a `DECISIONS_LOG.md` entry that says plainly it is a second one and
names the unification as the follow-up. Then decide on the unification with
two working examples in hand rather than none. The alternative — refactoring
the tutorial maths pipeline as a prerequisite — puts a large, risky change
in front of a small, valuable one, and tutorials are the surface with actual
students on it.

The glossary case is worth calling out separately: it is the one where the
data is *shared* between two renderers (build-time for tutorials,
client-side for dewmini's Library rail). Whatever is decided, those two must
agree, or the same definition will render differently in two places.

## 6. Restart and run all, as one action

**What.** One button: throw the interpreter away, then run every cell from
the top.

**Why.** The standard answer to "my namespace is in a mess", and — more
usefully here — the reproducibility check. If a notebook does not survive
this, it does not work; it only appeared to. Together with feature 1 this is
the complete lesson: *the counter shows you the problem, this proves you have
fixed it.*

**Extent.** Very small. Both halves exist and simply need wiring together:

- `engine.restart()` plus `dfs.reset()` — see `initExecutionSection()`
  (~2293) for the existing sequence, including its confirm dialogue.
- `runAllCells()` (~1072) for the second half.

**Watch out for.** `runAllCells()` already calls `resetPageState()`, which
is the *cheap* reset (clear and re-seed the namespace) rather than a full
restart — the distinction is documented in the comment at ~1064. Understand
which one you actually want before wiring; they are not the same, and the
cheap one is what "Run all" already gives you. If they turn out to be
equivalent in practice, that is worth saying, because then this feature is
just a label — and a label is still worth having if it is the label that
teaches the idea.

**Where.** Restart currently lives in Settings. This probably wants to be
nearer the notebook, but see the note in feature 3 about the toolbar having
just been thinned on purpose.

## 7. Two I would argue against

Recorded so they do not get proposed again without the counter-argument.

**Magics** (`%%time`, `%matplotlib inline`, `!pip install`). Invisible
non-Python syntax that works in a notebook and fails everywhere else. For
students who will be asked to write real `.py` files — PDP and CMPS both
require it — this teaches a dialect that breaks the moment they leave the
tool. `%%time` in particular has an honest Python answer (`time.perf_counter`)
that teaches something transferable.

**Modal keyboard commands** (Jupyter's Esc/Enter, `dd` to delete, `a`/`b` to
insert). Genuine speed for an expert, and a trapdoor for a beginner: press
Escape by accident and typing stops working, with nothing on screen
explaining why. Jupyter itself needs a help overlay for this. If any of it
is wanted, plain shortcuts that always mean the same thing are the safer
half of the idea.

## 8. Suggested order, and why

1. **Execution counters** (1) — cheapest, teaches the most, and is the
   foundation the next one leans on.
2. **Stale marker** (2) — ship with the above; together they are one
   coherent idea about what a notebook actually does.
3. **Restart and run all** (6) — very small, completes that idea.
4. **Run above / below** (3) — the practical tool, once the problem is
   visible.
5. **Maths** (4) — largest, highest ceiling, and needs §5 settled first.

An honest alternative order: if the *next* teaching block is maths-heavy,
feature 4 outranks everything else on this list regardless of cost, because
the other four make an existing tool clearer while that one makes it usable
for half the course.
