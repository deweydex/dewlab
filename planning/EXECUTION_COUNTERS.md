# Execution counters in dewmini

An execution counter is the small number Jupyter shows beside a cell as
`In [3]`. It says when that cell last ran, counting up across the session: the
first cell you run is 1, the next is 2, and so on, wherever they sit on the
page. A cell that has never run shows nothing.

dewmini does not have them. This document says why they are worth building and
what building them involves. It also records two features from Jupyter that
are deliberately not wanted, so that neither is proposed again without meeting
the argument against it.

**dewmini** is dewlab's browser Python workspace, a small notebook at
`compose/dewmini.html` driven by `compose/dewmini.js`. It runs real Python
through Pyodide in a Web Worker. It is not a tutorial page: tutorials are
generated by `build.py` and driven by `assets/tutorial-runtime.js`. The two
share an engine, which is why a change to the engine reaches both.

---

## Why a counter is worth having

The most confusing property of a notebook is that it runs **in the order you
press Run, not from top to bottom**. A student whose cell 2 depends on a name
defined in cell 5 has a notebook that works perfectly for them and fails for
everybody else, including for themselves tomorrow after a reload. Nothing on
the page says so.

dewmini makes this sharper than Jupyter does, because every tab shares one
namespace (`DEWMINI_WORKBENCH.md` §3). A name can therefore arrive from a cell
that is not even on screen.

A counter is also the cheapest thing that teaches something real here.
Reproducibility is a learning outcome rather than a nicety, and a counter makes
the failure visible instead of invisible.

---

## What it involves

The change is small: one integer on the cell, one counter on the notebook, one
badge in the cell header. Line numbers drift, so the function names below are
the durable anchor.

- `insertCellAt()` builds the cell shape, `{ id, type, content, output,
  error }`. It gains `count: null`.
- `executeCell()` increments a counter held for the notebook and assigns it.
- `createCellElement()` builds `.dm-cell-head`. The badge goes there.
- `runAllCells()` calls `engine.resetPageState()` first, so the counter resets
  there too. After a Run all the numbers read 1 to n from the top, which is
  exactly the point being taught.
- Restart, in `initExecutionSection()`, clears every count, because nothing in
  the namespace survives a restart.

**Counts do not survive a reload.** `saveState()` tolerates a missing field, so
adding one is safe either way, but the Python session itself does not survive a
reload. A count that did survive would be claiming something false. Clear them
when saved work is loaded.

**The export already has somewhere to put them.** nbformat calls this
`execution_count`, and dewmini's `.ipynb` writer currently writes `null` for
every code cell. Filling it in makes an exported notebook more faithful with no
further work.

**A test can hold the whole feature in one assertion.** Unit tests cannot see
this, so it goes in `tests/e2e/test_dewmini_workbench.py`: run cell 3, then run
cell 1, and assert the badges read 2 and 1.

## Two features argued against

**Magics**, meaning `%%time`, `%matplotlib inline` and `!pip install`. These
are invisible non-Python syntax that works inside a notebook and fails
everywhere else. Our students are asked to write real `.py` files on both PDP
and CMPS, so a dialect that breaks the moment they leave the tool costs them
something. `%%time` in particular has a plain Python answer,
`time.perf_counter`, which teaches something they can take with them.

**Modal keyboard commands**, meaning Jupyter's Escape and Enter modes, `dd` to
delete a cell and `a` or `b` to insert one. These are fast for an expert and a
trapdoor for a beginner. Press Escape by accident and typing stops working,
with nothing on screen to explain why. Jupyter itself needs a help overlay for
it. If some of the speed is wanted, plain shortcuts that always mean the same
thing are the safer half of the idea.
