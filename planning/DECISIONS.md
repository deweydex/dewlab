# Decisions Log

## Settled

| Area | Decision | Why |
|---|---|---|
| Core libraries | numpy, pandas, matplotlib only, for a tutorial page | All three ship as official Pyodide packages, loadable via a single `loadPackage()` call with no micropip step at all. Dropping sqlite removes the one library that needed unvendoring, and dropping openpyxl removes the one that needed micropip. dewmini (`compose/`), not being curriculum content, carries a wider default of its own — sqlite3 and Pillow beyond the three above (DECISIONS_LOG.md 7.78) — without changing this baseline for tutorials. |
| Data format | CSV, not Excel | Matches the Our World in Data (OWID) datasets already in use, and keeps the load sequence micropip-free. Excel support becomes an opt-in exception on a per-tutorial basis if a specific tutorial needs it, not a baseline dependency. |
| Interactivity layer | `tutorial_tools.py`: a small bridge between a student's cell and the page, providing `text_input`, `dropdown`, `button`, `show`, `show_table` and `check` | A cell needs a way to put something on the page and to read something back, and students should not have to learn a DOM API to do it. Nothing in it is assessment-shaped — no scoring, no submission, no record kept anywhere. |
| Visual identity | A tutorial house style of its own, sharing a visual family with the department's other teaching materials | A student should be able to tell at a glance that a page is practice rather than assessment, without the materials looking like they came from different places. |
| Asset strategy | Shared external CSS and JavaScript, not inlined into each page | A page that must run offline from a double-clicked file has to carry everything inside it. A hosted tutorial does not, and shared files in `/assets/` mean one edit updates every tutorial at once instead of every generated page needing to be patched. |
| Layout pattern | Prose block → executable cell → output area, repeated | Explanation, then the thing to try, then what happened. Keeping that rhythm identical on every page is what makes a series read as one tool rather than a folder of pages that happen to share a colour scheme. |
| Navigation | Persistent series table of contents + prev/next links across all generated tutorial pages | Needed now that there's a series rather than one standalone file. |
| Cross-tutorial data | Real files in a shared `/data/` folder, fetched at runtime, never duplicated per tutorial | One dataset, one file, referenced by however many tutorials need it. |
| Shared setup code | An authoring-time include directive, expanded by the build script | De-duplicates boilerplate at the markdown-source level. Each tutorial page is still an independent Pyodide instance at runtime with no persistent kernel across pages — the expanded cell re-executes every time; nothing is shared live. |
| Cross-tutorial links | A recognized markdown link syntax, resolved to a relative href at build time, with a build-time check that flags dead references | Catches a broken "see Tutorial 2" link before publishing, not after a student reports it. |
| Version scheme | A plain integer `version:` field per tutorial in frontmatter, bumped when executable-cell content changes | Semver's major/minor/patch distinctions don't map to anything here — the only question that matters is whether the code in a tutorial changed since a student saved progress against it. |
| Version compare on load | Match saved version against current page version; on mismatch, restore is still attempted, matched by stable per-cell `task_id`, with a visible but non-blocking notice | Matching by a stable per-cell id tolerates cells being reordered, or a new one inserted, far better than matching by position in a list — which silently restores the wrong work into the wrong cell. |
| Editor, v1 | A local GUI built on Milkdown (Crepe preset) — a live, borderless block editor, not a raw-text-plus-preview loop, with math (KaTeX) and code blocks (CodeMirror, syntax highlighted) native to the editing surface | Two authors, both comfortable with git, both preferring to work visually. Crepe is an editor pattern already familiar from other authoring work here, so reusing it means one editing experience to learn rather than two. |
| Math rendering | KaTeX, rendered in both the GUI editor's live view and the built student-facing page | Confirmed needed for Mathematics for IT content. Matches the toolchain already in use elsewhere (Milkdown's math support, markdown-it-texmath at build time), and renders at build time the same way the rest of the page does — no client-side LaTeX parsing cost for students. |
| Hosting | GitHub repo with a GitHub Actions workflow that builds on push to main and deploys straight to Pages | Editing markdown and pushing is the whole workflow — no separate manual build-and-commit-the-output step to forget. |
| Module and year metadata | A `module` and `year` field in frontmatter, free text/slug rather than drawn from a fixed list, with `/tutorials/` organized into one subfolder per module | Scope keeps growing — four modules confirmed for year one, a fifth as a colleague's pilot, more plausible later — and nothing about the build or navigation should need to change when one is added. `year` is an academic-year string (e.g. `2026-2027`), not a plain integer: the program is scoped one year at a time, so this records which year's offering a tutorial belongs to rather than tracking multi-year history. |
| Answer checking | A `check(actual, expected)` function in tutorial_tools.py, alongside the existing widget-bridge functions, rendering a pass/fail indicator in the cell's output area | Tutorials are confirmed ungraded, but some cells give students a self-check against a correct answer. Framed as formative feedback, not scoring — nothing is recorded, and it's unrelated to any institutional grade. |
| Palette and texture | Navy (#1B2A4A) and orange (#D4692A) on a serif (Georgia) base, continuing the existing teaching-materials identity; plus a texture panel — theme (system/light/dark), font (serif/sans/mono), size, line width, link colour, all applied through CSS custom properties | Confirmed. Consistent with the materials students already meet, rather than a new identity to learn. The texture panel is there because a reading surface a student can adjust is one more students can actually read. |
| Cell visual treatment | Prose blocks stay borderless and serif; exec cells get a light distinguishing treatment — a subtle border or background tint, line numbers, and standard syntax highlighting | Confirmed: enough visual difference to make the page structure scannable, without the heavier color-blocking that would fight the borderless prose style. |
| Code cell affordances | Line numbers and syntax highlighting via CodeMirror's own built-in extensions (`lineNumbers()`, a standard theme's language support) — no custom build required. A light per-cell hint affordance (a small icon showing author-written hint text on hover) is equally cheap, authored via an optional `hint:` field in the cell header — see CONTENT_AND_FILE_ARCHITECTURE.md | Line numbers and syntax colouring are free in the sense that matters — built-in CodeMirror behaviour, not something to design or build. A static author-written hover hint is just UI, same cost. This is distinct from live IDE-style hover documentation (hovering over `pd.read_csv` and seeing its real docstring/signature) — that needs a bridge from CodeMirror's hover extension into Pyodide's running Python to fetch real introspection data, which is a genuine feature to build, not a checkbox. See Assumed section below. |

## Assumed, not settled — flag if wrong

- scipy stays out unless a specific tutorial needs distributions or stats beyond what pandas/numpy cover. It's also an official Pyodide package, so adding it later is a one-line change, not a redesign.
- Editor preview opens the built HTML page via `build.py`'s output for a cell's actual Python execution, rather than running a live Pyodide pane inside the editor itself. The prose-and-math half of the editor is already live via Milkdown/KaTeX; this only concerns code output. Assumed as the cheaper default for now.
- Live, IDE-style hover documentation (real docstrings/signatures pulled from the running Pyodide environment) is a plausible v2, not committed for v1 — consistent with the plain-execution-before-bonus-layers priority already set for Phase 0. The light hint affordance above covers v1's needs at near-zero cost; the live version is real scope, not an extension of it.
