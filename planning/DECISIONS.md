# Decisions Log

## Settled

| Area | Decision | Why |
|---|---|---|
| Core libraries | numpy, pandas, matplotlib only | All three ship as official Pyodide packages, loadable via a single `loadPackage()` call with no micropip step at all. Dropping sqlite removes the one library that needed unvendoring, and dropping openpyxl removes the one that needed micropip. |
| Data format | CSV, not Excel | Matches the OWID convention already in use, and keeps the load sequence micropip-free. Excel support becomes an opt-in exception on a per-tutorial basis if a specific tutorial needs it, not a baseline dependency. |
| Interactivity layer | tutorial_tools.py, rebuilt from the exam tool's widget-bridge design (text_input, dropdown, button, show, show_table), stripped of exam-only concerns | exam_tools.py no longer exists to port, but its function signatures and behavior are documented well enough to rebuild against. A separate name signals it's tutorial-facing, not exam-facing — no task scoring, no integrity banner. |
| Visual identity | A new "tutorial house style," distinct from the exam theme, but sharing a visual family with whatever exam tooling gets built later | Keeps a tutorial from ever being mistaken for an active exam, without the two tools looking unrelated to each other. |
| Asset strategy | Shared external CSS/JS, not fully inlined | The exam tool inlined everything because it had to run offline, double-clicked, for exam integrity. That constraint doesn't apply to hosted tutorials. Shared `/assets/` files mean one edit updates every tutorial instead of hand-patching each generated HTML file. |
| Layout pattern | Prose block → executable cell → output area, repeated | The pattern the exam tool and the original index.html tutorial already validated, carried forward conceptually even though neither file survives to build from directly. |
| Navigation | Persistent series table of contents + prev/next links across all generated tutorial pages | Needed now that there's a series rather than one standalone file. |
| Cross-tutorial data | Real files in a shared `/data/` folder, fetched at runtime, never duplicated per tutorial | One dataset, one file, referenced by however many tutorials need it. |
| Shared setup code | An authoring-time include directive, expanded by the build script | De-duplicates boilerplate at the markdown-source level. Each tutorial page is still an independent Pyodide instance at runtime with no persistent kernel across pages — the expanded cell re-executes every time; nothing is shared live. |
| Cross-tutorial links | A recognized markdown link syntax, resolved to a relative href at build time, with a build-time check that flags dead references | Catches a broken "see Tutorial 2" link before publishing, not after a student reports it. |
| Version scheme | A plain integer `version:` field per tutorial in frontmatter, bumped when executable-cell content changes | Semver's major/minor/patch distinctions don't map to anything here — the only question that matters is whether the code in a tutorial changed since a student saved progress against it. |
| Version compare on load | Match saved version against current page version; on mismatch, restore is still attempted, matched by stable per-cell `task_id`, with a visible but non-blocking notice | Follows the task_id-matching approach the exam tool's load-JSON feature proved out, which tolerates cells being reordered or inserted between versions far better than matching by array position. |
| Editor, v1 | A local GUI built on Milkdown (Crepe preset) — a live, borderless block editor, not a raw-text-plus-preview loop, with math (KaTeX) and code blocks (CodeMirror, syntax highlighted) native to the editing surface | Two authors, both comfortable with git, both preferring to work visually. Crepe is already the editor pattern in use in Josh's own writing-app project — reusing it keeps the authoring experience consistent across projects instead of introducing a second one to learn. |
| Math rendering | KaTeX, rendered in both the GUI editor's live view and the built student-facing page | Confirmed needed for Mathematics for IT content. Matches the toolchain already in use elsewhere (Milkdown's math support, markdown-it-texmath at build time), and renders at build time the same way the rest of the page does — no client-side LaTeX parsing cost for students. |
| Hosting | GitHub repo with a GitHub Actions workflow that builds on push to main and deploys straight to Pages | Editing markdown and pushing is the whole workflow — no separate manual build-and-commit-the-output step to forget. |
| Module and year metadata | A `module` and `year` field in frontmatter, free text/slug rather than drawn from a fixed list, with `/tutorials/` organized into one subfolder per module | Scope keeps growing — four modules confirmed for year one, a fifth as a colleague's pilot, more plausible later — and nothing about the build or navigation should need to change when one is added. `year` is an academic-year string (e.g. `2026-2027`), not a plain integer: the program is scoped one year at a time, so this records which year's offering a tutorial belongs to rather than tracking multi-year history. |
| Answer checking | A `check(actual, expected)` function in tutorial_tools.py, alongside the existing widget-bridge functions, rendering a pass/fail indicator in the cell's output area | Tutorials are confirmed ungraded, but some cells give students a self-check against a correct answer. Framed as formative feedback, not scoring — nothing is recorded, and it's unrelated to any institutional grade. |
| Palette and texture | Navy (#1B2A4A) and orange (#D4692A) on a serif (Georgia) base, extending Josh's existing teaching-materials identity; a texture panel — theme (system/light/dark), font (serif/sans/mono), size, line width, link color, applied via CSS custom properties — carried over from the writing-app project's settings pattern | Confirmed. Keeps dewlab visually consistent with Josh's other materials and tools rather than inventing a new identity, and reuses a working, already-built settings pattern rather than designing one from scratch. |
| Cell visual treatment | Prose blocks stay borderless and serif, matching the writing-app aesthetic; exec cells get a light distinguishing treatment — a subtle border or background tint, line numbers, and standard syntax highlighting | Confirmed: enough visual difference to make the page structure scannable, without the heavier color-blocking that would fight the borderless prose style. |
| Code cell affordances | Line numbers and syntax highlighting via CodeMirror's own built-in extensions (`lineNumbers()`, a standard theme's language support) — no custom build required. A light per-cell hint affordance (a small icon showing author-written hint text on hover) is equally cheap, authored via an optional `hint:` field in the cell header — see CONTENT_AND_FILE_ARCHITECTURE.md | Line numbers and syntax coloring are "free" in the sense Josh meant — built-in CodeMirror behavior, not something to design or build. A static author-written hover hint is just UI, same cost. This is distinct from live IDE-style hover documentation (hovering over `pd.read_csv` and seeing its real docstring/signature) — that needs a bridge from CodeMirror's hover extension into Pyodide's running Python to fetch real introspection data, which is a genuine feature to build, not a checkbox. See Assumed section below. |

## Assumed, not settled — flag if wrong

- scipy stays out unless a specific tutorial needs distributions or stats beyond what pandas/numpy cover. It's also an official Pyodide package, so adding it later is a one-line change, not a redesign.
- Editor preview opens the built HTML page via `build.py`'s output for a cell's actual Python execution, rather than running a live Pyodide pane inside the editor itself. The prose-and-math half of the editor is already live via Milkdown/KaTeX; this only concerns code output. Assumed as the cheaper default for now.
- Live, IDE-style hover documentation (real docstrings/signatures pulled from the running Pyodide environment) is a plausible v2, not committed for v1 — consistent with the plain-execution-before-bonus-layers priority already set for Phase 0. The light hint affordance above covers v1's needs at near-zero cost; the live version is real scope, not an extension of it.

## Note on the lost source files

exam_tools.py and hvit_exam.html no longer exist. Where this document says a decision "follows," "rebuilds," or was "validated by" the exam tool, that means working from the specification captured here and in VERSIONING_AND_PROGRESS.md — not porting working code. The decisions themselves haven't changed; Phase 0 and Phase 2 in BUILD_PLAN.md are implementations from spec rather than ports.
