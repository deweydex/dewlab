Why a notebook cell needs to say what it is

A plan for a feature dewmini doesn't have yet — execution counters — written for anyone reading it cold. It explains what problem it solves, and why each small decision in its design turned out to be the shape it is.

The problem

In a notebook — dewmini's, or any other tool shaped like one — every cell shares one running program. Run cell three, then cell one, then edit cell two without re-running it, and the page still lists them in the order you typed them: one, two, three. But that is no longer the order anything actually happened in, and the page currently has no way to say so.

That gap causes a specific, common kind of confusion: a cell's output doesn't match what its code would currently produce, and there is nothing on the page telling you why. Was it never run? Run, then edited afterwards? Run before some other cell it depends on? All three look identical today — an output sitting under some code — and a reader is left to guess.

The fix is not clever. It's a plain, honest record: which cell ran, in what order, how long it took, and whether its code has changed since. The interesting part is not that idea — it's making that record show up clearly, on every kind of cell, without cluttering the ones that don't need it.

An identity, at a glance

Every cell gets a small label in its header: its number, and what kind of cell it is.

the identity pill

⋮Cell 1Python ⋮Cell 4SQL ⋮Cell 5HTML ⋮Cell 6CSS

Every cell, every type — numbered the same way, coloured differently.

It says the word Cell rather than leaving a bare number to imply it — four extra characters, and nothing left for a first-time reader to guess at. The type sits in the same label as the number, because both answer the same question — what is this, before I've read a line of it — and a reader shouldn't have to piece two separate badges together to get one answer.

why colour, too

Each type gets its own hue on top of its own word. In a notebook that mixes Python, SQL, and a bit of HTML, colour lets a reader sort cells by type without reading every label — but only ever on top of the text, never instead of it. A reader who can't tell two colours apart loses nothing, because the word was always there to read.

why the whole pill drags

dewmini lets you reorder cells by dragging them. An early version made only the small three-dot handle draggable — a precise target on an otherwise wide, inviting label, worse on a touchscreen than a mouse. Since the pill already shows exactly what you'd be picking up, there was no reason to make the target smaller than the label itself.

A line that says what happened

Underneath the code, a Python or SQL cell — the two kinds that actually run — reports what its last run was like, in one line:

the run line, in each state

Not yet run this session
Ran 1st in 340 ms
Ran 1st in 340 ms — edited since
Running… 1.6 s

One line, four states — order, duration, and staleness folded together rather than three separate badges.

Order and duration sit on the same line because a reader reads them together anyway — when, and how long. The "edited since" flag isn't a separate badge either: it's the same fact about the same run, so it belongs on the same line as the run it's describing. And while a cell is actually running, the time keeps counting up live — useful to watch, but deliberately not read aloud by a screen reader on every tick. A number changing ten times a second is noise, not news; the line still announces itself once, when the run finishes.

Cells that never run against the shared program — a Text cell, an HTML cell, a CSS cell used purely for styling — show no run line at all. A cell that can never go stale shouldn't carry a line that could be mistaken for saying it might.

Not every cell needs every part

Giving a cell a control it can't use is worse than leaving it off — it invites a reader to wonder what that control does. Four things vary by what kind of cell it is:

PythonSQLHTMLCSSText
Numbered, coloured label✓✓✓✓✓
Run line (order, duration)✓✓———
Collapse the code away✓✓—✓—
Renders, and stays quiet until touched——✓—✓

That last row is its own small idea worth naming: a Text or HTML cell is meant to be read, not run, so — like a Markdown cell in any other notebook tool — it renders by default and keeps its editing controls out of the way until you actually click into it. Nothing is removed while it's quiet, only made invisible to the eye; a keyboard user tabbing through the page can still reach and open it, even though a mouse user would need to hover first to see it's there.

Where your hands already are

Run and reset sit at the bottom of a cell, under the code, not above it. That mirrors where dewlab's tutorial pages already put their own Run button — and the reasoning is the same in both places: your cursor is wherever you just finished typing, at the bottom of what you wrote, not back up at the top. The next thing you do should be waiting where your hand already is.

What this leaves out, on purpose

  • No dependency graph between cells. A plain "Ran 1st, ran 2nd" answers when something ran without pretending to know something the notebook genuinely can't see — which cell's variables another cell actually reads.
  • No keyboard way to drag a cell — yet. Reordering cells still only works with a mouse or a touchscreen. That's a real gap, named honestly rather than left for someone to discover later.
Where this stands: this is a design, not a built feature — nothing above exists in dewmini today. The pieces it would lean on already do: dewmini already knows when a cell's code has changed since its last run, and already knows how to run a range of cells or restart the whole session. What's missing is only the counter itself, and the header shown here to display it.
